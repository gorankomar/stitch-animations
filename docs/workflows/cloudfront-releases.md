## Release procedure after cutover

- Fetch current `origin/main`, preserve unrelated work, combine approved source/assets/docs/instructions/tests and fresh dist outputs, and run `npm run validate:release` before merging.
- Main's workflow prepares a SHA-identified manifest covering the complete dist, uploads a unique `releases/<SHA>/` directory, and verifies every served file checksum/MIME/CORS before activating staging. A completed directory cannot be overwritten with different content. No destructive root sync or `--delete` is allowed.
- Each permanent channel file imports its chosen immutable `page-all-lite.js`. All imports then resolve inside that release directory. Upload assets before the entry and completion manifest. Serialize uploads/promotions/rollbacks with the workflow's shared concurrency group; do not bypass it with simultaneous direct CLI operations.
- Keep channel cache TTL zero, invalidate its exact viewer path on change, wait for completion, and verify its served body/CORS/cache header. Retain old release assets and pointer history. If a post-write verification fails, report that the pointer may have changed; explicitly restore the previous verified SHA and verify again.
- Agent checks staging's actual loader/imported release, desktop/mobile behavior, reduced motion where relevant, and Product Variety/wallet swap and Country Flags wherever present. Complete checksum verification alone is not visual approval.
- Production promotion requires explicit production authorization and a manually selected full SHA already active on staging. The script verifies the full release for the configured production origins. Production activation changes live animations WITHOUT a Webflow publish on pages already using the channel loader; report it as a production deployment, and verify the interactions.
- Rollback is the same manually authorized channel switch to a previous verified retained SHA; it can bypass the current staging match. No rebuild and no routine Webflow URL edits are needed.
- One-time Webflow loader routing chooses production only for the four configured production hosts and staging for the staging/Preview host. The identical router and `stitch-code-page-loader` ID prevent site/footer and Playground duplication. New production hosts must be added explicitly.
- Re-read Webflow saved custom code before draft/publication work; preserve unrelated code. Keep Preview using staging. Remove redundant component runtimes covered by the shared loader, preserving styles and markup.
- “Middle” is a legacy preparation-only alias: staging animation preparation plus saved Webflow drafts, stopping before page publication or production activation. Use publish to staging/production for normal releases; a GitHub-only merge can activate staging but never production.
- Webflow page publication and channel activation are distinct. Publishing production pages does not automatically promote animations; promoting animations does not publish page drafts. Select only authorized Webflow domains and record both states separately.
- Keep jsDelivr pinned SHA delivery as the verified fallback if needed. Provider changes require served-file and browser verification, plus explicit production authorization for live activation.

## Commands

Local preparation: `node scripts/cloudfront-release.mjs prepare FULL_SHA` after a full build. Do not commit `dist/release.json`: it is generated by CI using the actual merged commit.

AWS-enabled execution (normally only through GitHub Actions): `upload FULL_SHA`, `verify FULL_SHA`, `activate FULL_SHA staging|production`. See the admin handoff for required environment variables, supported workflow operations, cache configuration and rollback.
