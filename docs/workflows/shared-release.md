# Shared release

Normal destinations are **staging** and **production**. Local and Webflow drafts are preparation. Follow [publishing](publishing.md) for authorization, default scope, combined Webflow/animation changes and domain selection; [CloudFront releases](cloudfront-releases.md) covers deployment details.

1. Fetch origin and inspect current origin/main plus working-tree edits. Preserve unrelated work. Combine all approved chat-owned source/assets/effects/docs/instructions/tests with current main; never release an outdated feature branch.
2. Run `npm run validate:release`. It builds every shared entry/embed, tests fresh artifacts, and verifies dependency closure plus Product Variety/wallet swap and Country Flags. Commit fresh generated outputs for the approved change, preserving unrelated portable artifacts. Single-feature builds are insufficient.
3. Merge the validated work. Main's enabled workflow prepares a checksummed manifest, uploads the complete dist to a retained immutable `releases/<SHA>/` directory, verifies served bytes/MIME/CORS, then activates staging and waits for CloudFront invalidation. Read its actual outcome: merge/upload success alone is not activation success. Preserve the old release folders and root files; never use destructive root sync.
4. Save requested Webflow drafts and remove redundant component feature-module scripts/inline animation runtimes resolved by page-all-lite. Preserve styles, markup, component internals and unrelated custom code. The permanent site-wide and Playground routers remain unchanged. Verify new motion through the Playground staging channel; new code requires a staging release before Preview can use it.
5. For **publish to staging**, publish only the staging Webflow domain when changed page/markup/styles need publication. For animation-only changes, no Webflow publish is needed. Verify actual served channel/SHA and affected interactions; check desktop/mobile/reduced motion where relevant. Inspect required shared interactions wherever present.
6. For **publish to production**, use the exact staging-verified SHA. Dispatch `promote`, channel `production`, on main when animation promotion is needed. The protected environment requires user review; do not bypass it. Verify the activated channel and affected interactions. Publish required Webflow changes only to authorized production domains, accounting for other drafts and compatibility during cutover. Markup-only work can reuse the already verified production animation release.
7. Record release SHA, previous/new channel pointers, workflow/invalidation results, Webflow draft/publication state, domains and live behavior evidence. Restore the prior retained release with explicit rollback when authorized; coordinate any required markup rollback separately.

Preparation-only requests do not authorize production activation or Webflow publication. Old “middle” prompts mean staging animation preparation plus saved Webflow drafts, stopping before page publication. A GitHub-only merge can activate staging automatically but never production. Completion is the requested destination verified, or an accurate preparation/blocker report.

Emergency fallback: pinned jsDelivr can use a fully merged SHA containing all fresh committed dist files, after verifying the entire dependency set and obtaining authorization for the affected live destinations. Replace the shared routers consistently; do not append fallback scripts alongside active channels.
